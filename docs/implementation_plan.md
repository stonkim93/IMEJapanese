# 일본어 IME 버그 수정 및 개선 계획

현재 두 가지 주요 문제를 개선하기 위한 구현 계획입니다.

## 1. YN 변환(わ/を -> ゐ/ゑ) 한글 입력 버그 해결 및 3자리 코드 적용 확대

### 원인 분석
- `ゐ`와 `ゑ`의 코드를 091, 093에서 290, 294로 변경하면, 사용자가 `わ`를 입력하고 `Y+J` (091을 가리킴) 등을 타이핑할 때 `CharacterDatabase.ContainsCode(091)`이 False가 됩니다. 
- 현재 `Lang.cs`의 `ProcessKey`에서는 유효하지 않은 코드에 대해 예외 처리가 부족하여, 예외가 발생하거나 `null`이 반환되고, 이 키가 OS(Windows)로 그대로 넘어가 한글 모드에서 한글 자모가 입력되는 버그가 발생합니다.

### 해결 방안
1. **일본어 문자 코드 정규화 복원 (`JapaneseCharacter.cs` & `build_mozc_db.py`)**
   - `ゐ`와 `ゑ`는 원래 속성에 맞게 091과 093으로 유지합니다. (290, 294는 반탁음 영역이므로 구조상 맞지 않습니다.)
   - 대신 YN 변환을 위해 `JapaneseCharacter.cs`의 `NextVoicing()` 메서드에 예외 규칙(`090 <-> 091`, `094 <-> 093`)을 명시하여 `わ->ゐ`, `を->ゑ` 변환을 자연스럽게 지원합니다.
2. **`Lang.cs` 안정성 강화 (한글 입력 방지)**
   - `ProcessKey`에서 모음을 조합할 때 생성된 코드가 사전에 없는 경우(`!ContainsCode`), 예외를 던지거나 키를 OS로 넘기지 않고 **기존 문자를 확정하고 모음을 단독 문자로 출력**하도록 예외 처리를 추가합니다. 이를 통해 배열에 없는 문자를 조합하려 해도 한글이 튀어나오는 문제를 완벽하게 차단합니다.
3. **3자리 코드 활용 확대**
   - Mozc 오프라인 한자 변환 시 모르는 단어(Unkown Word) 처리에 문자 코드를 활용하여 일반 기호와 일본어 문자를 구분하고 페널티 비용을 조정합니다.

## 2. Mozc 오프라인 한자 변환 성능 극대화 (Google 온라인 수준 목표)

### 개선 방향
1. **미등록 단어 (Unknown Word) 처리 개선 (`MozcDictionary.cs`)**
   - 현재 사전에 없는 1글자 단어의 경우 `LeftId=0`, `RightId=0`, `Cost=10000`으로 하드코딩 되어 있습니다. ID 0은 Mozc에서 보통 BOS(문장 시작) / EOS(문장 끝)로 간주되므로, 이로 인해 연결 비용(Transition Cost) 매트릭스가 꼬이게 됩니다.
   - 이를 일반 명사나 독립 문자를 나타내는 기본 ID(통상 1934 등)로 수정하고, 3자리 숫자 코드를 분석하여 일본어인지, 특수기호인지에 따라 Cost 페널티를 다르게 부여합니다.
2. **Beam Search 너비 확장**
   - Viterbi 알고리즘 탐색 너비(Beam Width)를 15에서 50~100 수준으로 확장하여, 탐색 중 정답이 누락되는 현상을 방지합니다. 성능에 큰 무리 없이 정확도를 크게 높일 수 있습니다.
3. **단어 길이 가중치 도입**
   - 형태소 분석 및 문자열 부분 매칭 시 더 긴 길이의 단어 조합에 보너스 점수(Cost 감소)를 부여하여, 잘게 쪼개져서 오역되는 현상을 막고 문맥에 맞는 자연스러운 긴 단어가 우선적으로 선택되도록 개선합니다.
